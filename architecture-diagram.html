🛠️ Recommended Remediation Waves
1
Quick Wins (Hours)
  • Parallel repo polling — FuturesUnordered + semaphore (max 10 concurrent). Cuts poll cycle from 6s → ~200ms
  • Include queued runs in tokio::join!() — 4 calls parallel instead of 3+1 sequential
  • Render debouncing — requestAnimationFrame coalescing; only render visible tab
  • Add compound indexes — (repo_id, status), (repo_id, conclusion, started_at)
  • Search filter debounce — 150ms delay before re-render on keystroke
  • Stop hidden tab timers — disable duration timers for non-visible tabs
2
Architecture (Days)
  • Incremental state updates — replace full-state clone with delta messages. Only send changed repos/runs over WS
  • SQLite batch INSERTs — wrap per-poll upserts in single transaction. 1000 INSERTs → 1 transaction
  • Circuit breaker per repo — skip polling repos with N consecutive failures. Protect rate limit budget
  • Analytics cache coalescing — single-flight pattern: first request computes, others wait on same future
  • LRU ETag cache — replace HashMap with bounded LRU. Evict least-recently-used, not random
  • Poller health check — watchdog task + automatic restart on panic. Log staleness alerts
  • Pre-flight rate limit checks — check remaining before sending. Budget allocation per repo
  • Connection count CAS loop — compare_exchange instead of Ordering::Relaxed
3
Scale (Weeks)
  • WebSocket delta messages — send only changed fields. Reduces multi-MB broadcasts to KB-sized diffs
  • Virtual DOM / incremental rendering — update individual DOM elements instead of full innerHTML replacement
  • Bounded state with LRU eviction — cap PreviousRunTracker, expandedRuns, jobLogs. Prune entries older than 24h
  • Stream large log responses — server-side truncation before download instead of fetch-then-discard
  • Configure actix worker threads — tune for I/O-bound workload (2× CPU cores)
  • Fine-grained locks — per-repo RwLock instead of global state lock. Eliminates lock contention cascade
🛡️ Fault Tolerance Gaps
Single Points of Failure
  • F1: Poller task (single-threaded) — if tokio task panics, no state updates reach clients. No health check or restart mechanism
  • F3: Broadcast drops silently — let _ = ws_tx.send() discards errors. Clients miss updates without any indication
  • C1: Single SQLite connection — no pool, no failover. Poller + analytics + handlers all serialize on one connection
Degradation & Recovery
  • F2: No retry on transient failures — 500 errors → empty vec. Partial state persisted; frontend shows stale data without indication
  • F4: No structured error context — handler errors return vague messages. Users can't distinguish rate limit vs auth vs network
  • F5: No streaming initial state — multi-MB payload on new WS connection. Slow networks may timeout
  • M4: Webhook/poller race — webhook state changes silently overwritten on next poll cycle
